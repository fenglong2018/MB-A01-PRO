## 1. 用户 · Monday, Aug 17, 2026, 10:58 AM (UTC+8)

看下这个ADC和校准是不是不对，VBAT输入，然后经过1.2M和3.3M电阻分压输入到MCU的ADC-IN，MCU得到VBAT*3.3/4.5=VADC,VBAT=VADC*4.5/3.3,如果VBAT=4.2V，VADC应该是多少，是不是超过我们校准用的1.2V基准？

## 助手

先核对分压公式和校准基准，再对照工程里 ADC/VBAT 的实际实现。

## 助手

再核对这颗 MCU 的 ADC 基准：1.2V 是满量程，还是只用来反推 VDDA。

## 助手

分压公式和软件还原都对，**4.2V 时 VADC ≈ 3.08V，会高于 1.2V，但不会超出 ADC 量程**。1.2V 不是 ADC 满量程基准。

## 4.2V 时 VADC 是多少

硬件是：

```text
VBAT -- R16(1.2M) -- AD_BAT(PA4) -- R17(3.3M) -- GND
```

\[
V_{\mathrm{ADC}} = V_{\mathrm{BAT}} \times \frac{3.3}{1.2+3.3} = V_{\mathrm{BAT}} \times \frac{3.3}{4.5} = V_{\mathrm{BAT}} \times \frac{11}{15}
\]

代入 \(V_{\mathrm{BAT}} = 4.2\,\mathrm{V}\)：

\[
V_{\mathrm{ADC}} = 4.2 \times \frac{3.3}{4.5} = 3.08\,\mathrm{V}
\]

反推也一致：\(V_{\mathrm{BAT}} = 3.08 \times 4.5 / 3.3 = 4.2\,\mathrm{V}\)。

软件里用的是同一比例 `15/11`：

```26:28:BSP/adc/adc_bat.c
/* Vbat = Vpin * (R16+R17)/R17 = Vpin * 45/33 = Vpin * 15/11 */
#define BAT_DIV_NUM         15u
#define BAT_DIV_DEN         11u
```

## 3.08V 超过 1.2V 有没有问题

**没有问题。** 1.2V 不是 ADC 的满量程。

这颗 MCU 的 12 位 ADC 量程是 **VDDA（约 3.3V）**：码值 0 对应 0V，4095 对应 VDDA。内部 `ADC_CH_INT_VREF`（CH18，标称 1.2V）只是一个**已知电压通道**，用来反推实际 VDDA：

\[
V_{\mathrm{DDA}} = 1.2\,\mathrm{V} \times \frac{4095}{\mathrm{raw\_vref}}
\]

然后再用 VDDA 把 PA4 的码值换成引脚电压，再乘 `15/11` 得到 VBAT。流程是：

```201:204:BSP/adc/adc_bat.c
    /* VDDA = VREFINT * FULL / raw_vref */
    vdda_mv = ((uint32_t)ADC_BAT_VREFINT_MV * ADC_FULL_SCALE) / raw_vref;
    vpin_mv = (vdda_mv * raw_bat) / ADC_FULL_SCALE;
    vbat_mv = (vpin_mv * BAT_DIV_NUM) / BAT_DIV_DEN;
```

所以要比较的是 **3.08V 和 VDDA≈3.3V**，不是和 1.2V：

| 电压 | 值 | 含义 |
|------|-----|------|
| VBAT 满电 | 4.2V | 电芯 |
| PA4 上的 VADC | **3.08V** | 进 MCU 的模拟量 |
| ADC 满量程 | VDDA ≈ **3.3V** | 3.08V 低于此，不饱和 |
| VREFINT | **1.2V** | 只用来算 VDDA，不是量程 |

4.3V 时 \(V_{\mathrm{ADC}} \approx 3.15\,\mathrm{V}\)，相对 3.3V 还有约 150mV 余量，设计上也说得通。

`ADC_StartCalibration()` 是芯片内部失调校准，和 1.2V 无关；1.2V 通道是另一路“尺子”，用来量 VDDA 到底是不是刚好 3.3V。

## 小结

- 分压、还原公式、代码比例都正确。
- VBAT=4.2V → VADC=**3.08V**。
- 3.08V **大于** 1.2V 是正常的；**小于** 3.3V 才是不饱和的条件。
- 若把 1.2V 当成 ADC 满量程，才会误判“超量程”；当前实现没有把 1.2V 当量程用。

## 2. 用户 · Monday, Aug 17, 2026, 11:00 AM (UTC+8)

那我们ADC采用是不是没有滤波？没有的话我们讨论下滤波方式

## 助手

先把现有采集链路摸清：有没有硬件/软件滤波、平均次数、采样时间和后续怎么用这路电压。

## 助手

**现在几乎没有真正的滤波。** 只有同一次采样里连采 8 次算术平均，再加保护/预警的百分比滞回。时间上的电压滤波、硬件 RC，代码里都没有。

## 现状

| 环节 | 现在做什么 | 算不算滤波 |
|------|------------|------------|
| 硬件分压 | 1.2M + 3.3M，注释里没有 AD_BAT 对地电容 | 高阻本身有一点抗干扰，但源阻约 880kΩ，更需要电容帮 ADC 采样电容充电 |
| 采样时间 | 239.5 cycle | 为高阻建立时间，不是噪声滤波 |
| 软件 | `ADC_BAT_AVG_N=8` 连采平均 | 只压 ADC 量化/热噪声，窗口大约几毫秒 |
| 周期 | 1s 采一次，各次之间不相关 | 没有跨秒滑动/IIR |
| 滞回 | 7%/9%、12%/17% | 只稳住 level，**显示百分比仍会跳** |

8 次是背靠背连采，滤不掉工频、射频发射跌落、GNSS/PA 负载台阶。

另外，OCV 平台区很陡：40%～80% 大约 3.79～3.87V，约 **2mV 对应 1%**。12 位 ADC 还原到电芯大约 1LSB≈1.1mV，连采 8 次大约等效 0.4mV，平台区百分比仍可能 ±1～2% 抖动。LED 看电、报文里的两位电量都会跟着跳。

## 建议分三层，不要混成一种滤波

电量有两个用途，时间常数不该一样：

1. **保护/预警**（3.3V / 3.5V）：要跟得上真实掉电，不能滤太死。
2. **显示/报文百分比**：要稳，几秒到十几秒跟上即可。
3. **发射瞬间跌落**：那是负载，不是电量，应尽量避开，而不是靠平均“抹平”。

### 1. 硬件（优先确认原理图）

AD_BAT 对地加电容，和 880kΩ 等效源阻构成 RC：

| C | τ ≈ Rth·C | 作用 |
|---|-----------|------|
| 10nF | ~9ms | 帮 ADC 采样、滤毛刺 |
| 100nF | ~88ms | 更稳，一般够用 |
| 1µF | ~0.88s | 很稳，但充电/负载变化会拖尾 |

示位标这种慢变化电池，**100nF～1µF** 都合理。有电容后，软件平均可以少一点；没电容时，高阻分压更容易抖。

### 2. 软件快路径（每次 1s 采样内部）

保留连采平均，建议改成：

- **中值 + 平均**：5 或 7 点取中值，或去掉最大最小再平均，抗尖峰。
- 若板子有工频/开关噪声，8 点不要挤在 1ms 里，**间隔 1～2ms**，让窗口跨过约 20ms。

这一层只负责“这一秒的电压可信”，不算显示滤波。

### 3. 软件慢路径（跨秒，给百分比）

1Hz 上做 **一阶 IIR（指数滑动）** 最合适，RAM 只要一个 `uint16`：

\[
V_{\mathrm{filt}} = V_{\mathrm{filt}} + \frac{V_{\mathrm{now}} - V_{\mathrm{filt}}}{N}
\]

| N | 大约时间常数 | 观感 |
|---|--------------|------|
| 4 | ~4s | 还可能轻抖 |
| **8** | **~8s** | 看电/报文比较合适 |
| 16 | ~16s | 很稳，充电爬升会略钝 |

保护不要用同一个慢滤波：可以对 **原始秒电压** 判 PROTECT/WARN（已有滞回），对 **IIR 后电压** 再查 OCV 表得出 percent。这样低压保护不滞后，百分比不跳。

充电时电压上升快，若觉得 percent 跟不上，可以 CHARGE 下把 N 改成 4，或上升沿用更小 N。

### 4. 发射期：比滤波器更重要

RDSS 发信、PA 开、LED 大电流时，VBAT 会掉几百 mV，OCV 表会瞬间看成掉了十几%。建议：

- 发信/定位窗口 **跳过本轮采样**，沿用上一拍滤波值；或
- 本轮相对滤波值下跌超过例如 80mV 则判为负载跌落，**丢弃**。

没有这一步，再好的平均也会在报文电量上出现“发一次掉一截”。

## 不建议的

- **只把 `AVG_N` 加到 32/64**：连采仍在几毫秒内，对百分比抖动帮助有限，还拉长关中断式忙等。
- **单独做重 FIR/DMA 连续扫**：1Hz、两通道，过重。
- **只靠 level 滞回**：保护稳了，LED/报文 percent 照样跳。
- **保护也走 16s IIR**：低压关机可能来不及。

## 推荐落地（确认后可改代码）

1. 原理图确认 AD_BAT 对地电容；没有的话建议加 **100nF**。
2. 秒内：8 点平均保留，最好去极值或中值。
3. 秒间：percent 用 **N=8 的 IIR**；PROTECT/WARN 仍用未滤波（或轻滤波）电压 + 现有滞回。
4. 发信期间丢弃该次采样。

如果你拍板，我按上面 2～4 直接改 `adc_bat.c`（电容是硬件，软件侧只加注释）。N=8 还是 16、发信期是跳过还是跌落丢弃，也可以一起定。

我想一上电采集一次没有问题，但是后续的采集要改成同其他任务通知的形势启动ADC任务，你说下你的看法，然后那个任务启动后通知ADC采集任务启动比较合适？

## 助手

先摸清现有 ADC 周期采集和各任务（MODE、发信、看电、充电）的时序，再判断谁来通知采集更合适。

## 助手

这个改法方向对，也和后面低功耗（STOP0/STOP2）合拍：电量是慢变量，不必 1Hz 空转。上电采一次保留；之后改成 **被通知才采**。不要让 GNSS/RDSS/LED/KEY 去踢 ADC。

## 看法

ADC 任务继续留着，但线程改成 **等信号 → 采一轮 → 睡**，不要自己 `mdelay(1000)`。采集、换算、PROTECT/WARN 边沿、推 LED percent，仍放在 ADC 任务里，调用方只 `request`，不在 MODE/SESSION 里直接摸寄存器。

要注意三件事：

1. **保护/预警不再“随时自己发现”**。OFF/FORCE_OFF 可以不采；ON/ALARM 只要在每次会话开始前采一次，就能在开 GNSS/PA 前拦住低压。LOW_BATT 会推迟到下一次会话，产品上可以接受（ON 本就是 10min 一拍）。
2. **BATT 看电、CHARGE 流水** 不经过 SESSION，必须另有触发，否则关机放一夜再短按，LED 还是上电那次电压。
3. **绝对不要在 GNSS 定位中、RDSS 发射中采。** 那是负载跌落，不是 OCV。组包用的 percent 应是射频起来之前的缓存。

## 谁来通知：MODE 为主，SESSION 为辅

| 调用方 | 时机 | 为什么 |
|--------|------|--------|
| **MODE（主）** | 进入需要电量的状态时 | MODE 是唯一知道“现在要不要看电/要不要保护”的任务 |
| **SESSION（辅）** | 每一拍 `run_one_cycle` **开 GNSS 之前** | 报文电量、开射频前保护检查；此时电池最接近空载 |
| GNSS / RDSS | 不通知 | 正在耗电，采出来是假低压 |
| LED / KEY | 不通知 | LED 是消费者；KEY 太频繁且靠近 ISR |

MODE 适合通知的边沿（任务/状态“启动”，不是线程创建）：

| 状态进入 | 通知 ADC | 原因 |
|----------|----------|------|
| `BATT` | **要** | 5s 看电，必须是当下电压 |
| `CHARGE` / USB 插入 | **要**，并 **arm 慢周期** | 流水档位、≥98% 满电灯；充电是小时级，10～30s 一次即可 |
| `ON` / `ALARM` | **要** 一次 | 刚开机/刚告警先判断保护；后面交给 SESSION 每拍再采 |
| `LOW_BATT` | 不必再采 | 刚从 WARN 边沿进来，值还新 |
| `OFF` / `FORCE_OFF` | **停周期、不再采** | 省电；下次短按进 BATT 再采 |
| 退出 `CHARGE` | **disarm 周期** | 避免拔 USB 后还在 10s 空采 |

SESSION 适合的点只有一处：`run_one_cycle()` 里、`sim_present()` 之后、`gnss_start_fix()` **之前**。这一拍同步采完再决定是否开射频；`msg_pack` 继续读缓存的 `adc_bat_get_percent()`。发信结束不要再采。

CHARGE 的周期不要做成 ADC 自己默认 1s。由 MODE 进入充电时 `arm(10s~30s)`，退出时 `disarm`，策略在 MODE，定时可以放 ADC 内部。

## 建议的接口形态

```text
上电：adc_bat_init() → 校准 + 采 1 次（给 MODE 启动时 bat_is_protect）
之后：线程阻塞在 sem/mq

adc_bat_request()           MODE 异步踢一脚（BATT/ON/ALARM 进入）
adc_bat_sample_wait(to)     SESSION 开 GNSS 前同步采
adc_bat_arm_periodic(ms)    仅 CHARGE
adc_bat_disarm_periodic()   离 CHARGE / 进 OFF
```

MODE 不要等 ADC（BATT 动画用上一拍或几十毫秒后刷新即可）。SESSION 可以等，它本来就在阻塞等 GNSS/RDSS。

## 不建议

- 谁用电量谁踢：耦合散、必有人忘、发射中必有人误踢。
- 只让 SESSION 通知：BATT/CHARGE 会假。
- 只让 MODE 通知：报文电量绑不到“射频前空载”，ON 的 10min 拍也要对齐两次。
- 保留 1s 自采当“双保险”：等于没改，还挡休眠。

**一句话：上电自采一次；之后只认 MODE 的状态进入（外加 CHARGE 慢周期），以及 SESSION 每一拍开 GNSS 之前。** 若你认这套，下一步就把 ADC 线程改成等信号，并在 `mode.c` / `run_one_cycle()` 两处下通知。

## 4. 用户 · Monday, Aug 17, 2026, 11:18 AM (UTC+8)

另外还有一个问题，CHARGEING采集的电压会偏高，导致USB一插进去电量就抬高好多，这个我们一并讨论下处理方法

## 助手

充电时端电压会被抬高，OCV 表会把电量估高。先把充电检测、电量显示和现有采样点对上，再讨论怎么处理。

## 助手

插 USB 后电量猛涨，是 OCV 表被充电端电压骗了，不是分压算错。可以和「被通知才采」放在同一套规则里处理。

## 原因

现在 percent 一律是 **端电压 → OCV 表**。USB 一插，充电 IC 立刻灌电流：

\[
V_{\mathrm{测}} = V_{\mathrm{OCV}} + I \times R_{\mathrm{内}} + \text{保护管/线阻压降}
\]

平台区大约 **2mV ≈ 1%**。端电压瞬间抬 80～200mV，表上就会从例如 40% 跳到 70%～90%，电芯容量并没有变。CHARGE 流水用的就是这个 percent（30% / 70% / ≥98% 常亮），所以观感就是「一插就满了一截」。

板级只有 `USB_IN`，**没有充电电流、也没有 CHRG/满电脚**，所以没法用库仑计或芯片满电信号纠偏。

## 和「谁通知 ADC」怎么拼

充电时仍要采 **电压**（判断是否进入恒压、是否满电），但 **不要用这次电压去改 percent**。

| 时机 | 采电压？ | 更新 percent？ |
|------|----------|----------------|
| 上电（未插 USB） | 要 | 要（锚点） |
| `BATT` / SESSION 开 GNSS 前 | 要 | 要（空载 OCV） |
| **`USB_IN` 边沿** | 可采电压，**不要**用它查表 | **冻结**插拔前那次 percent |
| CHARGE 慢周期（10～30s） | 要 | 不按 OCV 跳变，只允许慢爬 / 判满 |
| **`USB_OUT` 后等 1～2s** | 要 | 要（松弛后的真 OCV，允许往下调） |
| GNSS/RDSS 工作中 | 不采 | — |

关键：MODE 进 CHARGE 时，ADC 里应已有「插 USB 之前」的空载 percent。事件驱动正好保证这一点——不要在 `USB_IN` 后再采一次当电量。

上电时 USB **已经插着**：第一次采样就是充电电压，没有锚点。这种只能走补偿或「先当未知、只流水、靠 4.2V 判满」，不要信开机那一拍的 OCV。

## 处理办法（从稳妥到复杂）

### 1. 冻结 + 限速爬升（建议做）

- `USB_IN`：`percent_ui =` 插前锚点，立刻抬高也不认。
- 充电中：电压照采，percent **每分钟最多 +1%**（或按标称容量/充电电流估，例如 600mAh、200mA → 约 2min/1%）。
- 上限卡在 97%，满电不靠 OCV 的 98%。
- `USB_OUT`：等 1～2s 再采，用 OCV 表纠正（可低于充电时显示的值）。

不需要电流采样，插进去不会跳档；充电几小时后流水 30→70 仍会慢慢变。时间常数用产品电池容量和充电 IC 电流估一个即可，不准也只是「充得显示偏慢」，比「一插跳满」好得多。

### 2. 满电改看电压平台，不看 98% OCV

充电到恒压时端电压会顶在约 4.20V，这时 OCV 表会提前报 100%。LED ≥98% 常亮应改成例如：

- \(V_{\mathrm{BAT}} \ge 4.18\,\mathrm{V}\) 且持续 **2～5 分钟** → 视为满，percent=100，三灯常亮。

没有 STAT 脚时，这是最实用的满电条件。

### 3. 固定压降补偿（可选，不能单用）

充电中查表前减一块典型压降，例如 80～150mV（要实验室用万用表对一下插 USB 瞬间跳变）。

单用会仍可能跳一档，因为 \(I \times R\) 随 SOC、温度、线材变化。适合作为限速爬升的辅助，或「上电就插着 USB」时的初值。

### 4. 不建议

- 充电也走同一张 OCV 表：就是现在的问题。
- 充电另做一张「充电电压–SOC」表：要标定充电电流，USB 口电流一变就失效。
- `display = max(旧值, 新 OCV)`：充电 OCV 虚高，会立刻顶满，比现在更假。
- 拔 USB 立刻查表：极化还在，会偏高；要等 1～2 秒。

## 建议的产品语义

```text
percent 分两路：
  空载（OFF/BATT/ON/ALARM 会话前）：电压 → OCV 表
  CHARGE：锚点冻结 + 限速爬升；满电 = 4.18V 维持
  拔出：延时采样，重新锚定 OCV
```

保护/预警在 CHARGE 里本来就忽略，继续用即可。报文不在充电态发，不受虚高 percent 影响。

LED：30%/70% 流水用 `percent_ui`；满电常亮用电压维持，不要用虚高的 98%。

如果你认「冻结 + 限速 + 4.18V 满电」这套，实现时可以和 ADC 改成通知启动一起做：MODE 只在进/出 CHARGE 时告诉 ADC `charge_enter(锚点)` / `charge_exit()`，爬升和满电判断都放在 ADC 任务里。充电电流（mA）和电池容量（mAh）若有标称值，限速会更准。

## 为什么压差就够

充电虚高的主因接近一块几乎固定的 \(I \times R\)，不是另一条完全不同的 SOC 曲线。插 USB 瞬间电压抬高 \(\Delta V\)，查表前减掉它，SOC 就能对上插之前的空载点——这正是「一插就跳档」要修的东西。

LED 只有 30% / 70% / 满电三档，报文电量也不在充电态发。一张表 + 一个 mV 偏移，分辨率已经够用。

两张表要在**同一充电电流**下把 0～100% 都标定一遍，还得和空载表在同一 SOC 对齐。电流一变（口线、适配器、进入恒压）、温度一变，第二张表一样不准，维护成本却高很多：Flash/JSON 里两套锚点，对不齐时 USB 一插照样跳。

## 压差怎么用

空载（BATT / 会话前）：\(V\) 直接查现表。

充电（`USB_IN` 为真）：

\[
V_{\mathrm{查表}} = V_{\mathrm{测}} - V_{\mathrm{offset}}
\]

\(V_{\mathrm{offset}}\) 先宏，以后 JSON 覆盖。标定很直接：同一块电池，记下空载电压，插 USB 稳定 1～2s 再读，差值就是初值，平台区（约 3.8V）最有代表性。

**恒压段必须单独处理**：到 4.18～4.20V 后电流在降，压差在缩小。若仍减满额 offset，4.20V 会被当成约 4.08V，**永远充不满**。建议：

- \(V_{\mathrm{测}} \ge 4.18\,\mathrm{V}\) 且维持一段时间 → 满电，不再减 offset；
- 或 offset 随电压线性收到 0（例如 4.10V 以上开始收）。

满电灯继续用电压维持，不要用「减完 offset 再查表 ≥98%」。

上电就插着 USB 时没有空载锚点，压差反而比「冻结上一拍」更有用，开机那次就能估。


读的时候：`cfg` 有有效值用 cfg，否则用宏。offset=0 表示关闭补偿，方便对比。

## 现状

- 片内 Flash **512KB**（`0x08000000`），链接脚本整段给程序；固件大约 **127KB**，后面很空。
- 页大小按手册 WRP「page 0～255」推算是 **2KB/页**。
- `cfg` 已有 RAM：`recv_id`、`device_id`、`pa_enable`、`charge_offset_mv`，文档写着 **Flash 固化未做**。
- RTC 校时标志走 **BKP**；STOP2 的 MODE/告警时间轴也规划在 BKP，不要进参数 Flash。

## 放什么、不放什么

| 放 Flash | 不放 Flash |
|----------|------------|
| `recv_id`、`pa_enable`、`charge_offset_mv` | MODE / ALARM 时间轴（BKP/RTC） |
| 用户改过的 `device_id`（可选） | OCV 表（固件 const） |
| 预留若干字节（出厂号、功率档等） | 每次 `$BDICP` 读到的卡号（会频繁写） |
| 以后：首次定位时间等真正要掉电保存的 | 电量 percent 缓存 |

## 地址：末尾 2 页（4KB）

```text
0x08000000  程序（链接脚本把 FLASH LENGTH 从 512K 改成 508K）
...
0x0807EFFF  程序上限
0x0807F000  参数槽 A   2KB
0x0807F800  参数槽 B   2KB
0x0807FFFF  Flash 末尾
```

放末尾的原因：程序从前往后长，OTA/烧录只要不「整片擦除」，参数能保住。双槽是为了写到一半掉电还能读到旧槽。

参数本身只有几十字节，**不必**上 EasyFlash/FAL；双页 + CRC 够用。

## 槽内格式（建议）

```text
magic    4   "SHY1"
ver      2   布局版本，加字段就 +1
seq      2   每次成功写入 +1，上电取 seq 更大且 CRC 对的槽
len      2
crc16    2   覆盖 payload（或整包除 crc）
payload     recv_id, device_id, pa_enable, charge_offset_mv, reserved[N]
```

`reserved` 先留 16～32 字节，避免每加一个配置就改地址。按 4 字节对齐，用芯片的字编程接口写。

上电：`cfg_init` 扫 A/B → 合法则灌 RAM，否则用宏默认。  
保存：写空闲槽 → 校验读回 → 再把旧槽 magic 清掉（或只靠 seq）。

## 何时写 Flash

`cfg.set` 先改 RAM（现行行为），再 **显式落盘**，不要每个字段写一次。

两种都行：

1. CLI 增加 `cfg.save`（推荐，产测改完点一次）。
2. `cfg.set` 成功后自动 `cfg_save()`——次数少，也可以。

不要在 GNSS/RDSS 路径里隐式保存。

## 和烧录 / 上位机

- 链接脚本缩短后，`.bin/.hex` 盖不到参数页；**整片擦除**仍会清参数，产线要约定：日常下载不要 Chip Erase，或擦后用 `cfg.set` + `cfg.save` 再写一遍。
- USB JSON **不必改格式**；上位机仍 `cfg.get/set`，多一个 `cfg.save` 即可。短报文协议不受影响。

## 不建议

- 参数跟程序叠在同一页（升级必丢）。
- 把整段 JSON 原文写入 Flash（浪费、难校验）。
- 一上来就上文件系统/EasyFlash（就这么几个整数）。
- 用 Flash 存 MODE/告警节奏（该用 RTC+BKP）。

## 实施顺序（若后面做）

2. 薄封装：`FLASH_Unlock` / 擦一页 / 按字写（`BSP/flash` 或放在 `cfg` 里）。
3. `cfg_load` 上电、`cfg_save` 双槽。
4. CLI：`cfg.save`，`cfg.get` 可带 `"saved":1`。
5. 文档写明：整片擦除会丢参数。

| 进 **ALARM / OFF / FORCE_OFF** | 写 MODE+prev；FORCE_OFF 时告警作废 |
| 告警正常结束（RAM 仍在，回 ON） | `alarm_active=0`，Flash MODE=OFF 或 FORCE_OFF（看当时电量） |

整包带 `magic + ver + seq + CRC`。写新槽成功后再算它是最新；读时两槽都校验，取 seq 大且 CRC 对的；都坏 → 宏默认，**身份不用垃圾数据**。

页擦几十 ms，和 GNSS/RDSS **禁止重叠**。STOP2 以后做进 OFF/FORCE_OFF 时：必须 **SAVE 完成再睡**（这轮先留接口，不实施 STOP2）。

等通知 +  上电同步 LOAD这两个没问题，空闲写我认为还有必要讨论下，这个会不会频繁写导致FLASH寿命超过？

## 助手

空闲写**不会多擦 Flash**。它只推迟「什么时候擦」，不增加次数。寿命只取决于 **什么事件会 dirty**。

## 助手

N32 这类片内 Flash 按保守 **每页约 1 万次擦除** 来算。双槽轮流擦，大约 **2 万次 SAVE** 才把参数区写坏。空闲写如果理解成「没事就刷一遍」，那才会伤寿命；我们要的不是那种。

---

## 空闲写是什么、不是什么

| | 说明 |
|--|------|
| **不是** | 定时器到了就写、idle hook 里写、1Hz 写 |
| **是** | 已经 dirty 了，等 GNSS/RDSS/透传不忙，再擦 **一页** |

次数 = dirty 次数（还可合并），和「等空闲」无关。空闲只是为了别跟发信抢 CPU。

---

## 什么事件才该 dirty（寿命就看这个）

| 事件 | 产品里有多勤 | 一次告警/一天大概几次 |
|------|----------------|------------------------|
| `cfg.set` / 出厂身份 | 极少 | 0 |
| 换北斗卡（号变了） | 极少 | 0 |
| 首次定位 Unix | 一辈子 1 次 | 0～1 |
| 进 **ALARM** | 落水/长按 | 1 |
| 进 **OFF** | 用户关机 | 一天几次都算猛 |
| 进 **FORCE_OFF** | 低电保护 | 很少 |
| 告警结束清窗，Flash 记 OFF | 每次战役 1 次 | 1 |

按一天关 10 次机、一年 3650 次 OFF，双槽也能用很多年。实验室连按开关机会快一些，仍远小于 2 万。

**绝对不能写 Flash 的：**

- 告警 2/5 分钟每一拍、ON 的 10 分钟每一拍  
- 每次 `$BDICP`（卡号没变）  
- `alarm_send_count`、电量、tick  

48h 告警若每拍都擦：约 **1000 次/战役**，十几次告警就能把页写废。墙钟只靠 **进 ALARM 写一次 `alarm_start_unix`**，复位用 `now - 锚点` 算相位，**不必把次数记进 Flash**。次数若要备援，放 **BKP**（不磨 Flash）。

---

## 再加两道「少写」

1. **内容没变不擦**：影子和槽里一样 → 不 dirty（重复进 OFF 且状态相同就跳过）。  
2. **合并**：短时间多个 dirty（关机紧接着保护）→ 只擦一页。

这样「空闲写」不会变成寿命问题；真有风险的是误把会话节拍当成 SAVE。

---

建议定死一句：**Flash SAVE 只允许身份/换卡/首次定位/进 ALARM·OFF·FORCE_OFF/告警结束清窗；2/5/10min 节拍禁止写。** 空闲只是这些事件的执行窗口。

若这句没问题，实现时就不会做周期刷写。要不要把 BKP 备援 `send_count` 也砍掉、复位只信 RTC Unix？

## 1. 能不能「只有进 FORCE_OFF 才写 Flash」？

**MODE / 告警：可以。身份：不行。**

- `recv_id`、设备编号、版本、卡槽、`charge_offset` 必须在用户 `cfg.set` / 换卡时就落 Flash，不能等到低电保护——可能永远等不到，授权就丢了。  
- 这些一年也没几次，不伤寿命。  
- `ALARM` / `OFF` / 告警结束：**不必写 Flash**。  
- `FORCE_OFF` 写 Flash 也不是必须：醒来本来就要 ADC，电量低进 `FORCE_OFF`、够电进 `OFF`。FORCE_OFF 时告警已作废，Flash 里记 MODE 意义不大。

所以 Flash 写成一句：**只为身份/配置（脏了才写）；MODE 和 48h 锚点不靠 Flash。**

---

## 2. 能不能放进 16KB Retention RAM？

**可以。** N32WB452 的 R-SRAM 是 `0x20020000`～`0x20023FFF`，STOP2 **能保住**（要开 PWR retention）。我们要的上下文只有一两百字节，16KB 足够。

必须先改链接：现在 `_estack = 0x20020000`，文档里堆还伸到 `0x20024000`，**已经碰到 R-SRAM**。要单独切出 `.rram` 段，**栈和堆不准进去**，只放一块带 magic+CRC 的 `nv_ctx`。

R-SRAM **保不住**的情况：

| 情况 | R-SRAM | 结果 |
|------|--------|------|
| 以后 OFF/FORCE_OFF 进 STOP2 | 保持 | 醒来可恢复 MODE/告警 |
| 真掉电 / 电池拔光 / POR | **丢** | 只能当冷启动：Flash 身份 + 看电量 OFF/FORCE_OFF |
| NRST / 看门狗 | 一般 **丢** | 同上，**告警窗回不来** |

STOP2 这条路径 R-SRAM 正好对上；「RAM 被清还要续 48h」若包含看门狗/掉电，R-SRAM 不够，除非再加 BKP（备份域，有 VBAT 就能留 Unix+MODE）。

## 3. 架构怎么改

从「Flash 任务扛所有」改成：

```text
冷数据（少写）          热数据（常改、STOP2 要活）
Flash 双槽 + CRC        R-SRAM nv_ctx + CRC
身份/recv_id/卡槽       MODE、prev
charge_offset           alarm_active、alarm_start_unix
版本/升级日期           （可选 send_count、末次坐标）
首次定位 Unix
```

任务也变轻：

| | 以前 | 调整后 |
|--|------|--------|
| 上电同步 LOAD | Flash | **先判 R-SRAM CRC**，再 LOAD Flash 身份 |
| 等通知 SAVE | MODE 也进 Flash | Flash **仅身份 dirty**；MODE 改 R-SRAM 就是 `memcpy`，无空闲写、无寿命问题 |
| 空闲写 | 避开射频再擦页 | **只对 Flash 身份还需要**；进 OFF/ALARM 不再排队擦页 |
| STOP2 前 | 必须等 Flash 写完 | **只保证 R-SRAM CRC 写好** 再睡 |

上电：

```text
R-SRAM 有效 → 用里面的 MODE/告警（ALARM 且未满 48h 则续）
R-SRAM 无效（冷启动）→ 不恢复告警；ADC：保护则 FORCE_OFF，否则 OFF
身份始终来自 Flash（CRC 坏则默认，不用错号）
```

nv 线程还在，但几乎只服务 **cfg.set / 换卡 / 首次定位**。MODE 不再经过它。

空闲写是不是可以写在空闲钩子里面？看门狗复位的情况确实要考虑，你再理下

## 助手

两件事要分开：**CPU 空闲钩子** 和 **射频空闲再写 Flash** 不是一回事。看门狗要用 **BKP**，不能只靠 R-SRAM。

---

## 1. 空闲写不要放进 idle hook

现在 idle 钩子是：没人 `pm_lock` → 进 **STOP0**。若在这里擦 Flash：

| 问题 | 原因 |
|------|------|
| 射频可能还在跑 | 钩子只表示 **MCU 没事做**。SESSION 在等 GNSS 超时、RDSS 等波束时，线程阻塞，CPU 照样进 idle，**定位/发信可能正忙** |
| 和 STOP0 打架 | 擦页要几十 ms，中途不能睡；钩子里还要先判断「在写就别 STOP」 |
| 容易被看门狗打死 | 擦 Flash 时取指会停，IWDG 若不喂狗就复位——正好是你要防的那种复位 |
| 钩子必须短 | RT-Thread idle 里做擦写，USB/定时器都会被拖死 |

所以：

- **idle hook**：继续只做 STOP0，不动 Flash  
- **身份落盘**：仍由 **nv 线程** 等通知，并且 **业务判定** GNSS/RDSS/透传都空了才擦  
- 擦的时候 **喂狗** + `pm_lock`，禁止进 STOP0/STOP2  

MODE/告警根本不必等空闲：改的是 BKP 寄存器，几微秒，MODE 线程里当场写完即可。

---

## 2. 看门狗复位：R-SRAM 不够，要用 BKP

| 复位 | 主 SRAM | R-SRAM 16KB | BKP + RTC | Flash |
|------|---------|-------------|-----------|-------|
| STOP2（以后 OFF/FORCE_OFF） | 丢 | **留** | **留** | 留 |
| **IWDG / NRST** | 丢 | **一般丢** | **留**（电还在） | 留 |
| 电池拔光 POR | 丢 | 丢 | 丢 | 留 |

告警 48h 锚点若只放 R-SRAM：STOP2 能醒，**看门狗一复位置告警就没了**。  
BKP 有几十个 16 位寄存器，够放下 `MODE + prev + alarm_active + alarm_start_unix + 小 CRC`。IWDG 后读 BKP 就能续 48h。

R-SRAM 仍有用，但定位改成 **大块、STOP2 专用**（末次经纬度、恢复 stub），不当告警的唯一本。

---

## 3. 三套库（看门狗算进去之后）

```text
Flash（少写，nv 线程）     BKP（常改，当场写）        R-SRAM（STOP2 大上下文）
身份 / recv_id / 卡槽      MODE、prev                 可选：末次坐标
charge_offset / 版本       alarm_active               以后 STOP2 恢复 stub
首次定位 Unix              alarm_start_unix
CRC 整槽丢弃               小 CRC
```

**谁在什么时候写：**

| 数据 | 写哪 | 何时 |
|------|------|------|
| 身份、换卡、`cfg.set` | Flash | nv 线程，**射频空闲**（不是 idle hook） |
| 进 ALARM / OFF / FORCE_OFF | **BKP 立刻** | MODE 线程，不擦 Flash |
| FORCE_OFF | BKP 清告警窗 | 仍不写 Flash MODE |
| 以后进 STOP2 前 | R-SRAM 填 ctx + CRC | 再 WFI；Flash 若有 dirty 必须先写完 |

**上电 / 看门狗醒来：**

```text
Flash LOAD 身份（同步，CRC 坏则默认）
BKP 有效？
  ├─ ALARM 且 elapsed<48h 且未保护 → 续 ALARM
  ├─ FORCE_OFF 或 ADC 已保护 → FORCE_OFF（告警已作废）
  └─ 其余 → OFF
BKP 无效（真掉电）→ 不续告警，只看 ADC：保护则 FORCE_OFF，否则 OFF
```

身份永不进 BKP（地方不够，也该掉电还在 → Flash）。

## 4. 和「空闲写」的关系（收口）

- **空闲写只针对 Flash 身份**，而且是 **会话空闲**，不是 CPU idle hook。  
- MODE/告警走 BKP，**不存在寿命问题，也不用排队**。  
- idle hook 保持「能睡就 STOP0」，不要塞擦写。

看门狗续告警靠 BKP + RTC Unix；STOP2 再叠加 R-SRAM；Flash 继续只扛身份。

## 29. 用户 · Monday, Aug 17, 2026, 2:39 PM (UTC+8)

BKP是什么意思？备用电源？

## 助手

**BKP 不是一块「备用电池」**，是芯片里的 **Backup 备份寄存器**（Backup Registers）。

N32WB452 在 **备份域** 里有一组小寄存器（本工程是 `BKP_DAT1`～`DAT42`，每个 16 位），RTC 日历也在这个域里。只要这个域还带电，里面的数和墙钟就还在，**主 SRAM、线程、普通 RAM 清掉也不影响**。

---

## 电从哪来

| 情况 | 备份域（BKP + RTC） |
|------|---------------------|
| 正常开机、看门狗复位、NRST | 还在（主电池还供着 MCU） |
| 以后 OFF 进 STOP2 | 还在（LSE/RTC 可继续跑） |
| 主电池拔光、彻底没电 | **没了**（示位标一般没有纽扣备用电池） |

所以它不是「另接一路备用电源」，只是 **同一块电池上、复位也清不掉的一小块记忆**。真没电了，只能靠 Flash 里的身份。

---

## 和另外两块怎么分

- **Flash**：没电也在，但能擦的次数少 → 身份、卡号、`recv_id`  
- **BKP**：复位/看门狗还在，写一下就完、不磨寿命 → MODE、告警开始 Unix  
- **R-SRAM 16KB**：主要扛 STOP2，看门狗一般保不住  

工程里 RTC「已校时」标志已经在用 BKP，不是新外设。

## 助手

先看现有 GNSS 报文和 RTC 校时入口，再给出可落地的方案，方便你核对后再写代码。

## 助手

建议这一期只接 **GNSS → RTC**，RDSS 先不碰。入口已经有了：`rtc_post_unix()`，缺的是日期和「未校时不能当墙钟」这两件事。

## 现状里真正的坑

GGA 只有当天时刻（`hhmmss`），没有年月日，**不能单独校时**。ATGM336H 默认一般会出 **RMC**（带 `ddmmyy`），ZDA 往往默认关，不必为校时再发 `PCAS03`。

另外，未校时并不等于 `rtc_get_unix()==0`。真掉电后日历会被写成 **2020-01-01**，读出来是一个很大的数。若这时把告警锚点写进 BKP，第一次 GNSS 校到 2026，`elapsed` 会变成好几年，**48h 会立刻结束、跳到 ON**。所以「接上 GNSS 校时」必须连这条一起改，不能只 `post` 一下。

RDSS 这边没有现成时间字段可解析，这一期不要为校时再开射频。

## 建议怎么做

**1. 谁转换、谁写入**

GNSS 在正常定位（`FIX_WAIT`）里顺带解析 RMC，拼出 UTC Unix，自己 `rtc_post_unix(..., RTC_SRC_GNSS)`。  
透传不要校时。CLI `test.rtc` 仍走现在的入口。GNSS **不写** RTC 寄存器，也不 include `mode`。

**2. 何时算一次有效时间**

定位仍以 **GGA quality ≥ 1** 为准。RMC 在等待定位时先缓存：`status=A`、日期合法。GGA 成功时若还没有 RMC，**先不要关电**，在同一 30s 超时里再等一句 RMC（通常同一秒就来）。超时仍有定位但没日期：照常上报定位，**跳过校时**。

RMC 两位年按 2000+ 即可。

**3. 校时策略（建议从简）**

| 情况 | 行为 |
|------|------|
| 未校时 | 第一次有效 GNSS 时间必须写入 |
| 已校时 | 每次有效定位都 `post`（2/5/10min 一次，写日历很轻）；差不到 2s 也可在 RTC 线程里直接丢掉，避免无意义改钟 |

不要「只校一次以后永不改」：LSE 会漂，告警 48h 要的是墙钟。

**4. 未校时的墙钟规则（建议一并定稿）**

- `rtc_get_unix()`：未 `rtc_is_synced()` 时对外返回 **0**（2020 默认历不算时间）。
- 进 ALARM 时若未校时：BKP 仍记 `alarm_active=1`，但 **`alarm_start_unix=0`（待定锚点）**，不要再写成 `1` 或 2020。
- 未校时期间：一直按 **2min**，不切 5min、不满 48h。
- **第一次校时成功**：把锚点锁成这次 GNSS 时间（告警窗从「第一次有真实时间」起算）。若你希望 48h 从按下 SOS 算起，RAM 里再记一个进入时的 `rt_tick`，校时时用 `gnss_unix - 已过秒数` 回推；差的只是第一次定位前那几十秒，产品上两种都能接受。我倾向 **锁成 GNSS 时刻**，实现更干净。
- 看门狗且 BKP 里锚点已是真 Unix：照旧 `resume`。锚点仍是 0：续 ALARM，但 48h 仍等下一次 GNSS。

**5. 组包 / 首次定位不要读 RTC**

`rtc_post_unix` 是异步的，组包时 RTC 可能还没写上。  
`gnss_fix_t` 增加 `unix_sec`（RMC 没有则为 0）：

- MBA01 当前时间戳：用这次 fix 的 `unix_sec`（现在还是填 0）
- `first_fix_unix`：第一次有效定位用 **fix 上的 unix**，不要用 `rtc_get_unix()`

**6. 初始化顺序**

`rtc` 和 `mode` 现在都是 `INIT_APP`，谁先跑不确定。建议 **RTC 改到 `INIT_ENV`**（和 cfg/ADC 同级），保证 `mode_init` 读墙钟时硬件和 `synced` 标志已经好。

**7. 时区**

NMEA 是 UTC，RTC 也按 UTC 存。转换不要走会带本地时区的 `mktime`（差 8 小时）。板子上用 `test.rtc` 对一次 GPS 时间即可确认。

## 建议先不做什么

- RDSS 校时  
- 为 ZDA 专门配模块语句  
- 未校时用 tick 撑满 48h（复位对不齐，和「墙钟」决策冲突）  
- GNSS include `mode` 去改锚点：第一次锁锚点由 **session 发现 `start==0` 且本次 unix>0** 再通知 mode 写 BKP

你核对这几条就行，尤其是 **未校时锚点=0** 和 **第一次校时从何时起算 48h**。没问题再说，我按这个改代码和文档。

## 36. 用户 · Monday, Aug 17, 2026, 5:44 PM (UTC+8)

什么时候进行校时我们再讨论下，我觉得也是不必要每次校时，校时用GNSS，不用RDSS

## 助手

校时和「每拍带时间」要分开：**报文时间戳可以每拍用 GNSS，写 RTC 不必每拍做。** RDSS 不用。

## 建议

**写 RTC（`rtc_post_unix`）只在这两种情况：**

1. **还没校过**（`rtc_is_synced()==0`，含真掉电后）：第一次有效定位且 RMC 日期合法，必须写。这是 48h / 复位续告警能成立的前提。
2. **已经校过**：只有 `|GNSS Unix − RTC| ≥ 60 秒` 才再写。2/5/10min 定位照常，多数拍只算时间、不改日历。

60 秒是给 LSE 长期漂移和人为 `test.rtc` 设偏留的门限；对 2min/5min/48h 节奏来说，差几十秒没有产品意义。LSE 在 48h 里通常只漂几秒，所以告警窗内几乎不会二次校时。

**不算校时、但建议每拍仍做：** 解析 RMC → 填这次 `gnss_fix_t.unix_sec`，给 MBA01 当前时间和 `first_fix_unix`。这只是组包，不写 RTC。

**明确不校：** 透传、无卡空过、GGA 成功但没有合法 RMC、RDSS。

## 不建议的两种

| 做法 | 原因 |
|------|------|
| 每拍都写 RTC | 没必要，也是你不想要的 |
| 校过一次直到掉电都不再写 | 48h 够用；若开机态挂很久，钟会慢慢偏，且无法纠正 CLI 设错的时间 |

若你更想「简单、不比偏差」：改成 **未校时写一次，之后每 24h 最多再写一次**。效果接近，只是 24h 内即使差了 2 分钟也不会纠正。

## 仍需你点头的一条（和「何时校」绑在一起）

未校时进 ALARM：BKP 锚点先写 `0`，一直 2min；**第一次 GNSS 校时成功后再锁 48h 起点**（建议就锁成那次 GNSS 时间）。  
若第一次校时就把 RTC 从 2020 一下子拨到现在、锚点却已经是假时间，48h 会立刻结束。

你定两件事就行：  
1. 再校用 **偏差 ≥ 60s**，还是 **每 24h 最多一次**；  
2. 48h 是否从 **第一次校时成功** 起算。  

定了再改代码。
